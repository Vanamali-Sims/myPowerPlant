1Executive summary

This report covers the construction and execution of an automated test suite for MyPowerPlant, a Victorian household solar, battery and VPP profiling application. Before this work the backend held 67 tests and the frontend had no test runner at all — the validation rules and KPI calculations that drive the product's financial estimates had no automated regression protection.

177 frontend tests were added across two suites, bringing the project to 244 automated tests, all passing. Executing them surfaced three defects, two of which materially affect the numbers shown to users.

Key findings

The appliance energy model overstates refrigerator consumption by roughly 30×. A single fridge is modelled at 322 kWh per week against a real-world 7–14 kWh. For any household that does not enter a monthly kWh figure — the least informed user, and the one most reliant on the estimate — the headline consumption figure is badly wrong.

Households with no solar are shown dollar savings they are not making. A household that answers "no solar" still receives a $33.69 per week saving and 51.7 kg of avoided carbon, calculated from a hypothetical array. The engine flags this figure as potential; the dashboard does not read that flag before rendering it as a dollar amount.

Neither defect was detectable by inspection or by using the app — both required calculating expected values independently and comparing. That is the argument for the suite existing.

Scope statement This report covers automated testing only. The manual functional cases (FUN-01…FUN-12) and the usability sessions are documented and ready but have not been executed. Section 7 states this position explicitly rather than implying broader coverage than was achieved.

2Testing approach

MyPowerPlant has no user accounts. A household is addressed by a server-generated identifier held in the browser. That single design decision drives the prioritisation: the identifier is the access control, so its unguessability carries more risk than any feature.

3.4 Handling of known defects

Two tests are marked it.fails. They assert the behaviour believed to be correct for defects KPI-01 and KPI-02, and currently fail — so Vitest records them as passing while the defect stands. Each is paired with a test pinning the behaviour the code exhibits today.

When a defect is fixed, its it.fails case begins failing loudly, prompting removal of the marker and its paired pin. This keeps the suite green without encoding the buggy behaviour as if it were correct — a distinction that matters, because a test asserting a bug silently blesses it.

KPI-01 · Refrigerator power rating

S2 — Major
Location
frontend/src/data/appliances.ts — refrigerator.powerKw
Found by
kpis.test.ts → a single refrigerator should use a realistic 5–20 kWh per week
Detected via
Independent plausibility check of modelled output

The refrigerator is assigned powerKw: 1.92 — the identical value to the air conditioner — and run for 168 h/week. Running continuously is correct for a fridge; the power figure is not.

1.92 kW × 168 h = 322.56 kWh per refrigerator per week

A domestic refrigerator uses roughly 1–2 kWh per day, i.e. 7–14 kWh per week. The model is out by a factor of about 30. On the baseline two-fridge profile, refrigeration alone accounts for 645 kWh of a 687 kWh modelled week — 94% of total household consumption, which is implausible on its face.

Cause. 1.92 appears to be a rated input power rather than an average draw. A fridge cycles at roughly a 15–25% duty cycle, giving an effective figure near 0.05 kW.

Impact. Affects only the modelled consumption path, used when a household has not entered a monthly kWh figure. That is precisely the least-informed user and the one most dependent on the estimate. Every downstream KPI inherits the error.

Recommended fix. Replace powerKw with a duty-cycle adjusted average draw, or retain rated power and set typicalHoursPerWeek to compressor run-hours. The first is clearer. Verify against the GEMS dataset the file cites.

KPI-02 · Savings shown to households without solar

S2 — Major
Location
frontend/src/lib/kpis.ts and DashboardView.tsx:62
Found by
kpis.test.ts → a household with no solar should not be shown dollar savings
Detected via
FUN-07 — deliberate test of the no-system household

When a household answers hasSolar: 'no', buildKpiReport still models a typical 6.6 kW array and carries those figures into weekly.savingsAud and weekly.carbonAvoidedKg. Measured output for a no-solar profile:

FigureValue returned
generationKwh131.95 kWh
savingsAud$33.69
carbonAvoidedKg51.70 kg

The report does set solarIsPotential: true, but DashboardView.tsx:62 renders weekly.savingsAud as a dollar KPI without consulting that flag. A household that has just told the product it has no panels is shown $33.69 per week it is not saving and 51.7 kg of carbon it is not avoiding.

Impact. The product's stated audience is households considering solar, so this is not an edge case — it is the main path for a large share of users. Presenting a hypothetical as an achieved figure could reasonably be read as misleading, which matters more than the arithmetic.

Recommended fix. Either zero these figures when solarIsPotential is true, or — better, since the potential figure is genuinely useful — relabel the cards in that case: "You could save ~$34/week" rather than "You saved $34". This is a product decision; the test currently pins existing behaviour so any change is deliberate.

VAL-14 · Client and server disagree on minimum battery units

S3 — Moderate
Location
validateProfile.ts vs backend/app/models.py:165
Found by
Cross-referencing both validation suites

The browser rejects batteryUnits < 1; the API schema permits ge=0. A value of 0 is therefore rejected in the interface and accepted by the API. The backend suite tests −1 and 9 but has no case for 0.

Impact. Low in practice, since the UI is the only caller. It matters as a policy question: should a household with no battery record zero units, or is "no battery" expressed another way? Whichever is right, the layers should agree.

Recommended fix. Decide the intended minimum, align both layers, and add a backend case for 0 asserting the decision.

5Verification by hand calculation

To verify the KPI engine independently rather than merely observing that it produces output, expected values for a representative household were calculated by hand from the documented methodology, then compared against the engine.

Inputs — baseline Kew household

FieldValueFieldValue
Postcode3101Solar12 panels × 400 W, facing S
Monthly bill$180BatteryTesla Powerwall 2, 20% reserve
Monthly usage540 kWhProviderAGL Energy
Peak periodEveningGrid factor0.77 kg CO₂-e/kWh

Hand calculation

1. Weekly consumption      540 ÷ 4                        = 135.0000 kWh

2. Solar generation        array  = 12 × 400 ÷ 1000       =   4.8 kW
                           daily  = 4.8 × 4.2 × 0.8 × 0.55 =   8.8704 kWh
                           weekly = 8.8704 × 7             =  62.0928 kWh

3. Self-consumption        direct   = min(62.0928, 135 × 0.4)  = 54.0000 kWh
                           leftover = 62.0928 − 54             =  8.0928 kWh
                           battery  = 1 × 13.5 × (1 − 0.20)    = 10.8000 kWh usable
                           shifted  = min(10.8, 4.0464, 54)    =  4.0464 kWh
                           self     = 54 + 4.0464              = 58.0464 kWh

4. Distributed to grid     62.0928 − 58.0464                   =  4.0464 kWh

5. Retail rate             180 ÷ 540                           = $0.333333 / kWh

6. Carbon avoided          4.0464 × 0.77                       =  3.1157 kg

7. Weekly savings          58.0464 × 0.333333 + 4.0464 × 0.18  = $20.0772

Caveat This profile supplies a monthly kWh figure, so the appliance model is not used for the consumption headline. Defect KPI-01 affects only the modelled path — a household that leaves monthly kWh blank — and is therefore not exercised by this example. A second worked example covering that path would strengthen the evidence.

6Continuous integration

Tests that are not run are worse than no tests, because they present the appearance of coverage. The suite is therefore wired into the existing security workflow rather than left as a local command.

JobRunsFails the build on
secret-scangitleaks over full historyAny secret, including one removed in a later commit
frontend-auditnpm audit, tsc -b, lint, npm testHigh-severity advisory, type error, lint error, failing unit test
backend-auditpip-audit --strictAny known vulnerable dependency
security-testspytest tests/ -vAny failing test

The npm test step was added as part of this work. The workflow triggers on every push to main, development and sec, on every pull request, and weekly on a schedule so that a newly disclosed advisory in an unchanged dependency is still caught.

Placement decision Executable tests deliberately live beside the code they test — backend/tests/ and frontend/src/lib/ — not inside the testing/ documentation folder. pytest.ini sets testpaths = tests and CI runs pytest tests/; a suite relocated under testing/ would be collected by neither and would silently stop running.

Execution columns, session notes and usability evidence were left deliberately blank. Recording a result that was not observed would make the entire body of evidence unreliable, including the parts that are genuine.

The usability material is complete and ready to run: five scenarios written as situations and goals rather than instructions (a scenario naming a button tests reading comprehension, not the design), a facilitator script with a redirect table for handling participant questions without coaching, and a note-taking template that separates observation from interpretation.

Closing assessment

The automated layer is now in reasonable shape: 244 tests covering every documented validation boundary, the KPI methodology, and the access-control model, all enforced on every push. The two Major defects it surfaced were invisible from the interface and would not have been found by manual testing, which is the clearest available evidence that the investment was worthwhile.

The material gap is human testing. The scenarios and script are ready; what remains is to run them and feed the findings back into the backlog.
